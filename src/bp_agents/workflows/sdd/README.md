# SDD Workflow

Ticket-driven autonomous software development. Discovers tickets from Redmine, dispatches coding agents through a skill pipeline, and merges approved work to main.

## Prerequisites

Complete platform Quick Start steps 1–2 (configure `.env`, build the sandbox image). Do **not** run `docker compose up` yet — create the target repo first.

## Setup

### 1. Create a target repository

The SDD agent writes code into a **target project** — a separate git repository. Must NOT be bp-agents itself.

Create it before starting the services: Docker creates a missing bind-mounted directory as root, which locks out your git client.

```bash
mkdir -p ~/projects/my-project
cd ~/projects/my-project
git init -b main
git commit --allow-empty -m "initial"
```

Set `BP_TARGET_REPO_PATH` in `.env` to that absolute path.

### 2. Start the services

```bash
docker compose up -d --build
```

### 3. Create a ticket

Open http://localhost:8082, sign in `admin` / `admin`.

1. Click **Projects** → **default**.
2. Click the **+** icon in the project menu → **New issue**.
3. Fill **Subject** (and optional **Description**).
4. Click **Create**.

Leave **Status** at its default `ready`. The orchestrator polls every 5 seconds and dispatches tickets in `ready` status.

### 4. Verify the SDD pipeline

```bash
uv run pytest tests/e2e/test_redmine_tracker.py tests/e2e/test_ticket_to_agent_output.py -v
```

## Troubleshooting

### Target repo is root-owned

If `docker compose up` created the directory before you did:

```bash
sudo chown -R $USER:$USER /path/to/my-project
cd /path/to/my-project
git init -b main
git commit --allow-empty -m "initial"
```

## Configuration

| Variable | Default | Purpose |
|----------|---------|---------|
| `BP_TARGET_REPO_PATH` | — | Absolute path to the target repo |
| `REDMINE_BASE_URL` | `http://redmine:3000` | Redmine API URL |
| `REDMINE_API_KEY` | — | Generated by redmine-setup; do not set manually |
| `REDMINE_PROJECT` | `default` | Redmine project identifier |

## Ticket lifecycle

Tickets move through states via the pipeline graph (`graph.py`).

Happy path:

```
ready → implementing → awaiting_review → reviewing
     → awaiting_verification → verifying → awaiting_approval → done
```

Branches:

- Review may request changes → `awaiting_revision` → `revising` → back to `awaiting_verification`
- Verification may fail → `awaiting_revision`
- Any stage failure sets `blocked` with a `blocked_reason`
